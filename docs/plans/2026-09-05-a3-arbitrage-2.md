### Comportement proposé si `site_id` manque

**Fail-closed, avec un écran d'arrêt** — le même motif que celui validé en
A11 pour le rôle du jour, pour ne pas inventer un second vocabulaire d'erreur :

- aucune requête n'est émise ;
- l'écran affiche « Site indéterminé — NEXUS ne peut pas savoir de quel
  commerce il s'agit. Reconnectez-vous. » avec un bouton **Réessayer** et un
  bouton **Se déconnecter** ;
- `console.error` (c'est une panne technique : un employé authentifié sans
  site est un état impossible, pas une absence normale — cohérent avec la
  règle A4-bis) ;
- **jamais** `|| ''` : une chaîne vide produirait une requête filtrée sur
  `site = ''`, donc 0 ligne, donc un écran vide indiscernable d'un commerce
  sans données.

Pour C4-e (Debug Créateur), le repli sert à **présélectionner** un site dans
une liste que le créateur peut changer. Le comportement proposé y est
différent : pas d'écran d'arrêt, mais **aucune présélection** — le créateur
choisit explicitement. Substituer Sainte-Marie ferait d'un site un défaut
implicite pour un utilisateur qui, par construction, les voit tous.

### Source cible

**`sites.timezone`, texte, `NOT NULL`, sans valeur par défaut.**

Je recommande `sites` plutôt que `station_config`, pour une raison qui n'est
pas esthétique : **`station_config` peut ne pas avoir de ligne** — c'est
exactement le cas des trois sites de `nexus-test` aujourd'hui. Tant que le
fuseau y habite, « pas de configuration » et « pas de fuseau » restent le même
état, et c'est ce qui rend un repli tentant. Dans `sites`, une ligne existe
toujours par construction : **un site ne peut pas exister sans fuseau**, et le
cas « absent » disparaît au lieu d'être géré.

Validation IANA : `pg_timezone_names` contient bien `America/Martinique`. Une
contrainte `CHECK` ne peut pas interroger une table ; la vérification se fait
par **trigger** `before insert or update`, qui rejette un nom absent de
`pg_timezone_names`. C'est auditable et testable, comme demandé.

`station_config.fuseau_horaire` ne doit **pas** être supprimée dans le même
lot : il faut d'abord que tous les lecteurs pointent sur `sites.timezone`.
Retrait dans un lot ultérieur, jamais simultanément — sinon on crée une
fenêtre à deux sources.

## 3 · C3 — le drapeau `parDefaut` est écrit, jamais lu

Vérifié, et le résultat confirme ton hypothèse.

**Écritures — 3, toutes dans `nexus-carburant-donnees.js` :**

```js
if (error) { … return { config: CUVES_PAR_DEFAUT, parDefaut: true }; }   // 569
if (data && data.cuves_carburants) return { config: …, parDefaut: false }; // 570
return { config: CUVES_PAR_DEFAUT, parDefaut: true };                     // 571
```

**Lectures dans le code applicatif : zéro.** Les cinq appelants de production
prennent uniquement `.config` :

| Appelant | Ligne | Forme |
|---|---|---|
| `NEXUS-Inventaire-v1.html` | 1742 | `const { config } = await …` |
| `NEXUS-Parametres-Station-v1.html` | 1734 | `const { config } = await …` |
| `NEXUS-Carburants-Pilotage-v1.html` | 1288 | `const [{ config }, …] = await Promise.all([…])` |
| `nexus-brief-donnees.js` | 188 | `cuvesConfig.config` uniquement |
| `NEXUS-Rapport-v1.html` | 374 | `cuvesConfigEco.config` uniquement |

Trois d'entre eux **déstructurent explicitement `{ config }`**, ce qui écarte
`parDefaut` à la ligne même où il arrive.

**Le défaut est donc bien double**, et le second est le plus grave : le signal
de prudence a été conçu, produit, puis perdu à l'usage. Le système *savait*
qu'il calculait sur des cuves qui ne sont pas les siennes, et ne l'a dit à
personne. Une valeur par défaut dangereuse est une erreur de conception ; un
avertissement émis et ignoré est une erreur d'architecture.

**Conséquence pour le lot :** supprimer `CUVES_PAR_DEFAUT` sans traiter les
cinq appelants ne ferait que déplacer le silence. Les deux se corrigent
ensemble.

## 4 · Comportement utilisateur quand horaires ou capacités manquent

Application de la règle A3 : **visible et bloquant si cela influence une
décision métier**. Le critère n'est pas l'écran, c'est l'usage.

| Écran / usage | Décision métier ? | Comportement proposé |
|---|---|---|
| Autonomie, seuil de commande, recommandation de livraison | **oui** | **Bloquant.** « Capacités de cuves non configurées pour ce commerce — NEXUS ne peut pas calculer une autonomie sans elles. » + lien vers Paramètres Station |
| Calcul de retard, rattachement d'un événement à un quart | **oui** | **Bloquant.** « Horaires de quart non configurés — impossible de dire si ce pointage est en retard. » |
| Brief, Rapport : sélection des carburants actifs | non (filtrage d'affichage) | **Visible, non bloquant** : bandeau « configuration incomplète », les carburants s'affichent tous |
| Paramètres Station : pré-remplissage du formulaire | non (c'est l'écran qui sert à configurer) | **Champs vides**, avec l'ancien jeu Sainte-Marie proposé comme **modèle explicite à cliquer**, jamais pré-rempli |

Le dernier cas est le seul où les valeurs de Sainte-Marie restent
légitimes — parce que l'utilisateur les demande, les voit, et les valide. Le
bouton B3 doit alors dire ce qu'il fait : « Pré-remplir avec les valeurs de
Vito Sainte-Marie Usine (station de référence) », et non « Réinitialiser ».

**Note sur `nexus-test` :** rendre ces écrans bloquants **arrêtera Carburants
et Inventaire dans la recette**, puisque `station_config` y est vide. C'est le
comportement correct, et c'est une conséquence à assumer explicitement : il
faudra configurer les trois sites de recette, ou constater que ces écrans
restent non éprouvés. À arbitrer avant A3-4, pas après.
